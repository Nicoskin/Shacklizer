# Шакалайзер

Портит фотографии так, будто они приехали по видеосвязи через дырявый
канал. Не «сожмём jpeg до кашицы», а настоящая потеря UDP-пакетов:
съехавшие макроблоки, вертикальные подтёки, призраки прошлого кадра,
разъехавшийся цвет.

**Сайт: <https://example.github.io/jackal/>** — ничего ставить не нужно,
всё считается прямо в браузере, фотография никуда не уходит.

## Как это работает

Ключевая мысль, из-за которой картинка именно «плывёт», а не просто
мылится: в H.264 кадр почти целиком собирается из предыдущего по векторам
движения. Ошибка, один раз заехавшая в кадр, не исчезает со следующим
пакетом — она едет дальше вместе с движением и живёт до тех пор, пока этот
кусок не обновят целиком.

Движков два.

### Настоящий H.264

Тут ничего не имитируется. Картинка правда кодируется x264, поток режется
на NAL-юниты (один NAL = один слайс = одна RTP-посылка = один UDP-пакет),
часть юнитов выбрасывается или бьётся побайтно, и это скармливается
настоящему декодеру с включённым error concealment. Артефакты получаются
ровно те, что рисует живой декодер.

В браузере это ffmpeg.wasm: ядро на 32 МБ тянется с CDN один раз и дальше
живёт в кэше. В десктопной версии — обычный `ffmpeg` из `PATH`.

Главная ручка здесь — **период intra-обновления**. Реальные видеозвонки
лечатся от потерь тем, что по кадру ползёт полоса intra-блоков и постепенно
чинит картинку. Чем длиннее период, тем дольше живёт однажды заехавший
артефакт: 8 кадров — лёгкая рябь, 30 — от лица мало что остаётся.

### Симуляция

Своя модель поведения декодера при потерях, на numpy (и её же порт на
типизированные массивы в браузере). Отдельно хранится `base` — то, что
передатчик хочет показать, — и `E`, накопленная ошибка декодера. На экране
всегда `base + E`, а по кадрам с `E` происходит следующее:

* едет по вектору движения — ошибка расползается;
* обнуляется на intra-блоках — кусок «чинится»;
* переписывается на потерянных блоках, где декодер выкручивается как
  умеет: тянет блок из старого кадра по протухшему вектору, размазывает
  последнюю удачную строку вниз или просто морозит картинку.

Считает мгновенно и ничего не качает, но артефакты придуманные. Настоящий
H.264 выглядит лучше.

В обоих движках пакеты теряются не поодиночке, а всплесками — модель
Гилберта-Эллиотта, как в реальной сети. Отсюда характерные горизонтальные
ленты: один потерянный пакет = одна полоса макроблоков.

## Пресеты

| Алиас | Название | Что это |
|---|---|---|
| `light` | Лёгкий лаг | дешёвая камера и узкий канал, но всё цело |
| `bad` | Плохая связь | мыльно, местами куски съехали |
| `jackal` | Шакал | пересвет, мыло, лицо расползлось |
| `broken` | Разрыв связи | полосы тянутся из позапрошлого кадра |
| `datamosh` | Датамош | длинные всплески потерь, всё уезжает в одну сторону |

## Локальная версия

Кроме сайта в репозитории лежит десктопное приложение и CLI на Python —
им удобнее гонять фотографии пачками.

```bash
pip install -r requirements.txt
```

Окно с превью и ручками (или двойной клик по `Шакалайзер.bat`):

```bash
python app.py
```

Из командной строки:

```bash
python -m jackal photo.jpg -e ffmpeg -p jackal
```

Шесть вариантов одной фотки, чтобы выбрать удачный:

```bash
python -m jackal photo.jpg -n 6
```

Пачкой по папке:

```bash
python -m jackal ./album -o ./out -p broken
```

Любой параметр переопределяется поверх пресета:

```bash
python -m jackal photo.jpg --set loss=0.3 --set refresh=30
```

`python -m jackal --list` покажет пресеты, `--help` — все ключи.

## Что где лежит

```
docs/            сайт (GitHub Pages)
  js/h264.js       движок настоящего H.264 на ffmpeg.wasm
  js/sim.js        движок-симуляция
  js/presets.js    пресеты и описания ручек
  vendor/          склейка ffmpeg.wasm (воркер нельзя грузить с чужого домена)
jackal/          python-пакет
  core.py          движок-симуляция
  ffmpeg_engine.py движок настоящего H.264
  cli.py           командная строка
app.py           десктопное окно на tkinter
```
